# Building a Microsandbox-Style Sandbox Manually

## 1. What were we trying to understand?

The goal was not simply to use Microsandbox.

The goal was:

> **Understand what is happening underneath a Microsandbox-style sandbox and reproduce the core technology ourselves using Rust.**

We wanted to answer:

- Where does the application filesystem come from?
- How does an OCI/Docker image become a filesystem?
- How does that filesystem get inside a microVM?
- What actually creates the VM?
- Where does the guest Linux kernel come from?
- How does the application get executed?
- Can we do all of this without Docker?

The answer turned out to be:

```text
OCI image
    ↓
OCI layers
    ↓
rootfs
    ↓
libkrun
    ↓
libkrunfw
    ↓
KVM
    ↓
Linux microVM
    ↓
application
```

---

# 2. The important components

There are several different technologies here. They solve different problems.

## OCI

**OCI = Open Container Initiative**

OCI defines standards for container images.

An OCI image essentially describes:

```text
What filesystem should the application see?
What layers make up that filesystem?
What configuration belongs to the image?
```

For example, Alpine Linux is available as an OCI image.

We pulled Alpine directly from Docker Hub without Docker.

---

## Docker Hub

Docker Hub is simply the registry in this experiment.

We used its registry API directly:

```text
Docker Hub Registry
        ↓
OCI image metadata
        ↓
OCI filesystem layers
```

Docker itself was NOT involved in running the container.

This was important because we wanted to understand the underlying mechanism.

---

## OCI Image Index

When we requested:

```text
alpine:latest
```

we did not immediately receive a single filesystem.

We received an:

```text
application/vnd.oci.image.index.v1+json
```

This is basically a list of images for different platforms.

For example:

```text
amd64
arm64
arm/v6
arm/v7
386
ppc64le
riscv64
s390x
```

Our machine/VM is x86_64, so we selected:

```text
architecture = amd64
os = linux
```

That gave us this manifest:

```text
sha256:d56c381f961d307a21b3ca004cf1e3910f106644aefb1f43e654c8a56c4fd395
```

---

# 3. OCI Image Manifest

The amd64 manifest told us what makes up the actual Alpine image.

It contained:

```text
config
layers
```

The important part was:

```text
layers:
    sha256:e2de96513ba9eb53b431787ec8a65cdde380ac4772a3e4c4b714dcfde2a102b5
```

The layer was:

```text
application/vnd.oci.image.layer.v1.tar+gzip
```

and approximately:

```text
3.85 MB
```

So now we knew:

> This compressed tar archive contains the filesystem contents of Alpine.

---

# 4. Pulling the layer manually

We downloaded the layer directly from the registry:

```text
/v2/library/alpine/blobs/<digest>
```

We saved it as:

```text
alpine-layer.tar.gz
```

Then extracted it:

```text
rootfs/
```

The result was:

```text
rootfs/
├── bin
├── dev
├── etc
├── home
├── lib
├── media
├── mnt
├── opt
├── proc
├── root
├── run
├── sbin
├── srv
├── sys
├── tmp
├── usr
└── var
```

This is the critical point:

> **The OCI image has now become an ordinary Linux root filesystem directory.**

There is nothing magical about the rootfs.

It is just filesystem contents extracted from OCI layers.

---

# 5. Why `/bin/echo` existed

We checked:

```bash
ls -l rootfs/bin/echo
```

and got:

```text
/bin/echo -> /bin/busybox
```

Alpine uses BusyBox for many standard Unix commands.

Therefore:

```text
/bin/echo
     ↓
/bin/busybox
```

So our Alpine rootfs already contained the executable needed for the test.

---

# 6. Now comes libkrun

This is where the container-like filesystem becomes a VM.

We installed:

```text
libkrun
libkrun.dev
libkrunfw
```

using Nix.

This was a major simplification.

Instead of manually building:

```text
libkrun
Rust dependencies
C headers
guest payload
kernel-related components
build dependencies
```

we could simply get the packaged components from Nix.

---

# 7. What is libkrun?

`libkrun` is the microVM runtime/library.

Our C program talks to libkrun through its C API.

For example:

```c
krun_create_ctx();
```

creates a VM context.

Then:

```c
krun_set_vm_config(ctx, 1, 128);
```

configured:

```text
1 vCPU
128 MB RAM
```

Then:

```c
krun_set_root(ctx, "/home/oqxo/microvm/alpine/rootfs");
```

told libkrun:

> Use this directory as the guest's root filesystem.

Finally:

```c
krun_start_enter(ctx);
```

started the VM.

---

# 8. What is libkrunfw?

We also installed:

```text
libkrunfw
```

This provides the guest payload consumed by libkrun.

We confirmed that it exports:

```text
krunfw_get_kernel
krunfw_get_version
```

And we confirmed that:

```text
libkrun.so
```

dynamically depends on:

```text
libkrunfw.so
```

So the relationship is approximately:

```text
our program
     ↓
libkrun.so
     ↓
libkrunfw.so
     ↓
guest kernel/payload
```

The important point:

> We did not have to build a Linux kernel ourselves.

libkrun/libkrunfw already provided what was necessary.

---

# 9. What is KVM?

KVM is the Linux kernel's virtualization interface.

Think of it as the mechanism that allows a program to say:

> Give me hardware-assisted virtualization so I can run a guest OS.

We initially got:

```text
Error creating the Kvm object: Error(13)
```

This was a permissions problem accessing:

```text
/dev/kvm
```

We checked:

```bash
ls -l /dev/kvm
```

and saw:

```text
crw-rw---- 1 root kvm ...
```

Our user wasn't initially in the `kvm` group.

We fixed it with:

```bash
sudo usermod -aG kvm $USER
```

and restarted WSL.

After that libkrun could access KVM.

---

# 10. First proof: the VM actually booted

Before using Alpine, we ran libkrun with:

```c
krun_start_enter(ctx);
```

without providing a root filesystem.

The result was:

```text
Kernel panic - not syncing:
VFS: Unable to mount root fs
```

This was actually a useful result.

It proved:

```text
libkrun
   ↓
KVM
   ↓
guest kernel
   ↓
kernel booted
   ↓
no root filesystem
   ↓
kernel panic
```

So we knew the VM itself was working.

---

# 11. Second proof: using the WSL root filesystem

We then tried:

```c
krun_set_root(ctx, "/");
```

The VM successfully booted into a shell:

```text
#
```

Inside it:

```bash
uname -m
```

returned:

```text
x86_64
```

and:

```bash
ls
```

showed the Linux filesystem.

This proved that libkrun could expose a directory as the guest root filesystem.

---

# 12. The important experiment: Alpine

Then we replaced:

```c
krun_set_root(ctx, "/");
```

with:

```c
krun_set_root(
    ctx,
    "/home/oqxo/microvm/alpine/rootfs"
);
```

Now the VM was using:

```text
Alpine rootfs
```

instead of:

```text
WSL rootfs
```

This is the important connection:

```text
OCI layer
    ↓
extracted
    ↓
Alpine rootfs
    ↓
krun_set_root()
    ↓
microVM
```

---

# 13. Running an application

We then used:

```c
const char *argv[] = {
    "/bin/echo",
    "hello",
    NULL
};

const char *envp[] = {
    NULL
};

krun_set_exec(
    ctx,
    "/bin/echo",
    argv,
    envp
);
```

This tells libkrun:

> Once the guest is running, execute `/bin/echo` with `hello` as its argument.

Then:

```c
krun_start_enter(ctx);
```

starts the VM and enters the configured execution path.

The result was:

```text
ctx = 0
vm_config = 0
root = 0
exec = 0
/bin/echo hello
```

So we successfully executed an application using an OCI-derived filesystem inside a libkrun microVM.

# 15. Where Microsandbox fits

A Microsandbox-style system is essentially building a usable product around this kind of infrastructure.

Conceptually:

```text
             Microsandbox
                   │
        ┌──────────┴──────────┐
        │                     │
    OCI images          sandbox management
        │                     │
        ▼                     │
      rootfs                  │
        │                     │
        └──────────┬──────────┘
                   ▼
                libkrun
                   ▼
                  KVM
                   ▼
               microVM
                   ▼
              application
```

The exact implementation details of Microsandbox can contain additional components and optimizations, so we should not assume every internal detail is identical to our experiment.

But we have reproduced the **core conceptual path**.

# 16. Why Nix was such a big help

This was probably the biggest practical discovery during the experiment.

Without Nix, we would have had to worry about:

```text
building libkrun
building libkrunfw
finding compatible dependencies
installing development headers
linking libraries
library versions
runtime library paths
build tools
```

Nix gave us packaged components:

```text
nixpkgs
   │
   ├── libkrun
   ├── libkrun.dev
   └── libkrunfw
```

We installed them directly:

```bash
nix profile install nixpkgs#libkrun
nix profile install nixpkgs#libkrun.dev
nix profile install nixpkgs#libkrunfw
```

Then we could immediately inspect:

```text
libkrun.h
libkrun.so
libkrunfw.so
```

and start experimenting with the API.

So instead of spending days on build infrastructure, we spent the time understanding:

```text
OCI
  +
rootfs
  +
libkrun
  +
KVM
```

That is exactly what we wanted.

# 17. The mental model to remember

The most important distinction is:

### OCI does NOT create the VM.

OCI gives us the **filesystem/application image**.

```text
OCI
 ↓
rootfs
```

### libkrun does NOT download Docker images.

libkrun receives a filesystem/rootfs and creates the microVM.

```text
rootfs
 ↓
libkrun
 ↓
microVM
```

### KVM does NOT understand OCI.

KVM provides hardware virtualization.

```text
libkrun
 ↓
KVM
 ↓
CPU virtualization
```

### libkrunfw provides the guest payload used by libkrun.

So:

```text
OCI      → filesystem
libkrun  → microVM runtime
libkrunfw → guest payload
KVM      → hardware virtualization
```

# 19. What we have NOT implemented yet

Our current implementation is intentionally small.

We have NOT yet built:

- OCI registry client in Rust
- OCI manifest parser in Rust
- automatic platform selection
- layer downloader in Rust
- layer extraction in Rust
- multiple-layer merging
- OCI whiteout handling
- container/image configuration handling
- networking
- sandbox resource policies
- filesystem isolation beyond the VM root
- process lifecycle management
- snapshotting
- a Rust CLI
- a server/API
- automatic cleanup

Those are the next layers.

The important thing is that we don't need to solve all of them at once.

# 21. The biggest takeaway

The experiment changed the mental model from:

```text
"Microsandbox somehow runs containers."
```

to:

```text
"An OCI image is basically filesystem data.
Extract that filesystem.
Give it to a microVM runtime.
Boot a guest.
Run the application inside it."
```

And the core stack is:

```text
        OCI
         │
      rootfs
         │
     libkrun
         │
     libkrunfw
         │
        KVM
         │
      microVM
         │
     application
```

We have now manually demonstrated this entire critical path on WSL2.

This is a good **baseline note** to keep. From here, the natural next step is to replace the manual `curl + tar` work with a small **Rust OCI image puller**, while keeping libkrun exactly as we have it.
